# devref

A loose warehouse of reusable, copy-paste-ready instruction and attitude fragments for agentic development work.

This repository is **not** a standard, policy framework, specification, requirements set, application guide, or general development ruleset. Nothing here is active by default. The contents are simply useful pieces of promptcraft collected for selective reuse when drafting project briefs, issue prompts, research tasks, review instructions, or autonomous execution runs.

Think of it as a toolshed: some tools are complementary, some overlap, some contradict each other, and some are only useful in unusual circumstances. Choose the pieces that fit the job.

## Ground rule

The existence of an instruction fragment in this repository gives it no authority over any project. Copying or explicitly incorporating a fragment into a brief is what makes it relevant to that work.

In particular, rules or terminology from one project must not silently become constraints on another project merely because an agent has seen or remembered them.

## Shelves

The files are grouped only to make useful fragments easier to find:

- [`autonomy.md`](autonomy.md) — persistence, carte blanche, bounded work, merge authority, checkpoint behaviour.
- [`exploration.md`](exploration.md) — mad-scientist research, competing prototypes, anomaly chasing, convergence.
- [`scope-and-containment.md`](scope-and-containment.md) — project boundaries, blast radius, trusted/untrusted execution, reversible work.
- [`risk-and-load-bearing.md`](risk-and-load-bearing.md) — labware, load-bearing work, downstream consequence, promotion boundaries.
- [`review.md`](review.md) — self-review, independent review, multiple reviewers, proportional scrutiny.
- [`verification-and-evidence.md`](verification-and-evidence.md) — observable evidence, exact contracts, baselines, known-good vectors.
- [`resource-use.md`](resource-use.md) — token economy, compute-rich exploration, cheap probes, diminishing returns, salvage.
- [`repository-work.md`](repository-work.md) — repo-native completion, issues, merges, docs, fresh-state checks.
- [`continuity-and-handoff.md`](continuity-and-handoff.md) — scratchpads, handoffs, resumption, context reconstruction.

These categories are shelving, not an ontology. A fragment should make sense when copied out of its file and pasted into a fresh brief.

## What belongs here

A fragment is worth keeping when it captures instructural nuance that is broadly reusable enough that you might plausibly want to paste it into a different agent brief months later.

Useful fragments are generally:

- self-contained;
- concrete enough to change agent behaviour;
- short enough to paste without dragging in an entire methodology;
- independent of hidden definitions elsewhere in the repository;
- allowed to overlap or contradict other fragments.

Do not "resolve" contradictions merely for tidiness. `Continue until productive work is exhausted` and `Stop after the requested artifact` are both useful tools for different jobs.

## Adding material

When a conversation, project, failure, successful run, review pattern, or odd edge case produces a reusable paragraph of instruction, salvage it here. Strip away project-specific names when that improves reuse, preserve them when they are essential to the behaviour, and optimize the result for copy/paste rather than theoretical completeness.

There is no requirement to make the warehouse internally consistent, complete, or elegant. A rusty tool that reliably works still belongs in the shed.
